# CSV突合ルール監査・STAGING対応（2026-10-16 改訂）

## 重要：旧版の誤実装を撤回

最初の試験版では、応募CSVの `応募求人ID` と求人CSVの `求人管理番号` を突合する独自フォールバックを入れてしまった。**既存Web版にこのフォールバックは存在しないため撤回し、GitHub上の `CsvImportLogic.html` から削除した**。また、Web版で定義されていない「雇用形態区分」「職種コード」「勤務場所名1」「県コード1」からの独自補完も削除した。必要な追加対応は、今後Web版と整合する仕様として別途検討する。

## 確認した正式な処理（Sheets版に移植）

1. **ファイル単位で形式を判定**：
   - A：`企業コード`、`仕事番号`または`お仕事NO`、`応募日時`または`応募日`
   - B：`応募先企業ID`、`応募求人ID`、`応募者ID` をすべて備える
   - 一致しなければ `GENERIC` と分類（ただし必須項目検証は行う）
2. **列名を正規化**：仕事番号は `仕事番号`→`お仕事NO`→`応募求人ID` の順に最初の非空値。応募日時、氏名、企業ID、媒体、対応状況、雇用形態、求人備考、勤務地名、住所も元Web版の候補順に正規化。Bの勤務地住所は都道府県＋市区町村＋詳細住所を連結。
3. **応募CSVの重複除外**：応募年月（YYYYMM）＋氏名で重複と判定し、最初に現れた行だけを残す。氏名はブラウザ内での判定・文字種分類のあと送信対象から除外。
4. **求人CSVのJOIN**：企業IDの前後空白を除去して大文字化、仕事番号の前後空白除去・大文字化・末尾 `_[0-9]{3,8}` / `§`以降の除去。**企業ID＋正規化仕事番号だけでJOIN**し、同一複合キーの求人CSVは先頭行を採用。
5. **求人管理番号**：求人画像Workerなどで使うが、**応募とのJOINには使わない**。応募CSVに`応募求人ID`がないAタイプであれば`仕事番号`／`お仕事NO`を使う。
6. **求人属性fallback**：求人CSVが一致していなければ、応募CSVに含まれる仕事名・職種・雇用形態・勤務地・備考・募集背景などを使う。求人CSV固有の給与・画像・Indeedタグは推測しない。求人分析情報の有無と求人CSV JOINフラグを混同しない。
7. **勤務地・居住都道府県の一致判定**は応募CSV側の勤務地と居住住所から計算し、求人CSV側の住所へ差し替えない。応募数の判定はWeb版に合わせて応募日時の有無で計算。
8. **職種／雇用形態コードの扱い**：Web版で明示的な変換がない生CSVコードは自動的に`コード:4`などへ加工しない。必要なら新規のマスタ変換仕様を決める。

## 2026-10-16の受領求人CSV

- 添付された求人CSVはCP932で正常に読み取れた。509データ行、企業IDは全件同一、507行は仕事番号を持ち、2行は仕事番号空欄。
- 現時点で応募CSVの現物は受領していない。**求人CSVの読み取りができたことと、応募CSVとの突合が成立することは別**。
- 低い突合率は、両CSVの企業ID・仕事番号の比較、対象期間の違いを確認して初めて原因が特定できる。番号を推測して別キーに読み替えるのは避ける。

## セッション状態がSTAGINGのまま残った場合

`内容を確認`はブラウザ内の計算のみ。一方`全件更新を実行`が途中で中断された場合は`STAGING`の作業タブが残る。

1. `有効応募分析 → 取込状態を確認` を開く。
2. `STAGING`で**現在処理中の人がいないことを確認したうえで**、`中断したCSV取込を破棄`で作業分だけ消す。正常に公開済みのデータは維持される。
3. `PUBLISHING`や`RECOVERY_REQUIRED`なら作業破棄はせず、復旧コマンドと現在の状態を確認する。
4. GitHubでの変更はApps Scriptエディタに自動反映されない。
