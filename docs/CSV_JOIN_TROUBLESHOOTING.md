# CSV突合率低下・STAGING残留への対応（2026-10-16）

## 発見経緯

シート版アップローダーの確認画面で、応募CSVの重複除外後の件数に比べて求人CSVとの突合が非常に少なく見える事象と、再取込時に「別のCSV取込が進行中」と表示される事象が報告された。

## 調査で確定したこと

- 提供された求人CSVはShift_JIS（CP932）で正常にデコードでき、**509データ行**あった。
- **求人CSVの企業IDは全行で同一**。仕事番号は507行に値があるが、**数字だけの仕事番号は0行**。求人管理番号は数字列。
- 取込前の確認画面で表示される件数は**ブラウザ内での照合結果**。この段階ではデータをSheetsへ書いていない。シートの数値／文字列セル型が直接原因とは考えにくい。
- 求人CSVに「勤務場所名1」「勤務地住所1」「県コード1」「雇用形態区分」「職種コード」など、旧ロジックが十分に補完していなかった列名がある。
- ただし**応募CSVの実際の仕事番号／応募求人ID列は未確認**なので、「突合率が低い原因は必ず管理番号との違い」と断定しない。取得時点の求人CSVが応募当時の過去求人を含んでいない可能性もある。
- 画面の「求人分析マスタ」件数は応募CSV内の求人属性でも増えるため、「求人CSVと突合できた求人件数」とは意味が違う。

## 対策

1. **仕事番号での同一企業ID照合を引き続き最優先**。
2. 仕事番号で一致しなかったときに限り、応募CSVの`応募求人ID`と求人CSVの`求人管理番号`が**完全一致し、企業IDも同じ場合**に補助照合する。重複する管理番号は安全のため補助照合しない。管理番号の数字だけで他企業を照合しない。
3. 管理番号経由で突合した場合は、保存する`仕事番号`を求人CSVの正式な仕事番号へ置き換え、後続のJOINや求人マスタで整合させる。
4. 求人CSVの`勤務場所名1`を勤務地名称、`県コード1`を47都道府県の名称、`勤務地住所1`を勤務地の都道府県補完に利用する。職種・雇用形態が応募CSVにも無い場合、元求人CSVのコードを意味不明な日本語に変換せず`コード:...`として保持する。
5. 取込前の確認画面で`求人CSV行数`、`仕事番号で一致`、`求人管理番号で一致`、`求人CSV仕事番号キー数`、企業ID不一致・仕事番号欠損などの診断件数を表示。
6. 求人CSVの内部`備考`は、そのまま分析用`求人備考`へ自動マッピングしない。応募CSVの`求人備考`・`掲載仕事備考`は全文保存対象のまま。

## 残留した取込状態の復旧

`内容を確認`はブラウザ内のみでGASの取込状態を変更しない。しかし、前回`全件更新を実行`が途中で中断すると、`STAGING`が残り、新たな`beginVASImport`を一定時間拒否することがある。

1. メニュー`有効応募分析 → 取込状態を確認`で状態を確認する。
2. **STAGING**で、誰も実際に取込処理中でないと確認できれば、`有効応募分析 → 中断したCSV取込を破棄`で未完了の作業用データだけ削除する。前回正常に保存された応募／求人は残す。
3. **PUBLISHING／RECOVERY_REQUIRED**なら`中断したCSV取込を破棄`は使わず、`旧データを復旧`と状態表示に沿って処理する。
4. 変更したGitHubコードはGoogleのバインドGASへ**自動反映されない**。今回の差し替え対象は`gas/CsvImportLogic.html`、`gas/CsvImport.html`、`gas/04_CsvUpload.gs`。既存テンプレートは作り直さない。
5. まず架空データを使って再試行し、実CSVでは上記の診断件数を確認する。

## テスト

`tests/csv-import.test.cjs`で、**架空のCSV_B管理番号と求人管理番号の同一企業照合、別企業で不一致、求人の列別名補完、個人情報をペイロードへ残さないこと**を検証。セッション状態と全件更新のモックテストは`tests/import-lifecycle.test.cjs`を継続。

**注意**：Google Sheets上での実CSVの再取込・実応募CSVとの突合率は、ユーザー環境で差し替えたあとに検証が必要。GitHub側のテスト合格だけでは実環境の成功を保証できない。
