# GAS CSV取込：型エラー修正と性能改善（2026-10-16）

- 対象：`valid-app-sheets` の既存**コンテナバインドGAS**。GitHub Pages版への転換は保留。
- 状態：**GitHubコード修正・モックテスト通過**。利用者の実Google Sheetsにおける実測／本番CSV成功はまだ未確認。
- 実報告：応募元2,912件、重複除外459件、分析対象2,453件、求人CSVと2,450件が一致（3件の仕事番号空欄）。求人CSV509行、求人分析マスタ188件。ここまでのWeb版互換JOINの修正は成功している可能性が高い。
- 残った問題：`送信データに許可されない型が含まれています` およびGASへの分割送信・シート保存の遅さ。

## 原因・対策の対応

| 課題 | コード上の原因・推定 | 今回の修正 |
|---|---|---|
| 保存時の型エラー | 作業シートに書いた日付文字列が、`getValues()`で`Date`として返る可能性 | `vasSafeCell_`で妥当なDateを日本時間の日付文字列に正規化。データセット・列名が分かる安全なエラー表示も継続 |
| 取込開始が遅い | `92_運用管理`に複数項目をセットする際、1項目ずつ繰り返し読み書き | `vasStateBulkSet_`により多項目を一括更新 |
| 通信往復が多い | 1回の`google.script.run`で最大200行を送る構造 | 200行のチャンクは維持したまま、最大3チャンクを`appendVASImportBatch`へまとめて送る |
| 転送データ量の過大化 | 多数の行を1回で送ると失敗・遅延リスクがある | ブラウザ側で1回約25万文字、GAS側で30万文字を上限に抑える |
| 完了反映が遅い | `20_突合データ`の本番コピーを500行ごとに行う | 1,000行ずつの一括読込・書込に変更 |
| 正常完了時の運用状態更新が遅い | 世代ID、最終日時、状態を複数回書込 | 保存後に一括更新 |
| 成功状態の誤表示リスク | 本番書込完了前に正常状態を書き得る | 本番タブの`SpreadsheetApp.flush()`後に`READY`を確定。最終確定の失敗時は復旧コピーから旧データを戻し旧世代IDを復元 |
| ボトルネックが見えない | 全体で「待ち時間」としか表示されない | ブラウザ処理、受入準備、GAS転送、本番反映を分けて時間表示 |

2. [`gas/05_CsvPublish.gs`](../gas/05_CsvPublish.gs)：本番1000行単位、完了時の状態一括更新、READY確定とロールバック強化
3. [`gas/CsvImport.html`](../gas/CsvImport.html)：最大3チャンクを1回送信、転送サイズ制限、各段階の時間表示
4. [`tests/import-lifecycle.test.cjs`](../tests/import-lifecycle.test.cjs)：テスト追加（GASエディタへの転記は不要）

- **`CsvImportLogic.html`・`CommonMasters.html`・`00_Config.gs` 等は今回の差分変更なし**。前回のWeb版互換仕様がすでに反映されていれば差し替え不要。

## 想定する処理回数の変化

今回の応募2,453件、求人分析マスタ188件において、応募の送信は200行区切りで**13チャンク**。求人マスタは1チャンク。画像候補も1チャンクに収まる場合は**合計15チャンク**となる。

- 旧構成：`appendVASImportChunk`を**15回**呼び出す。
- 新構成：最大3チャンクずつまとめるので、通信量の上限に触れなければ`appendVASImportBatch`を**5回**呼び出す（データ量の上限により6回以上になることもある）。
- 通信回数の削減が目的であり、GASでの実処理秒数が必ず3分の1になるとは限らない。最終的な更新時間はバックアップコピーやGoogle Sheets側の書込負荷にも依存する。

## 実環境での試験順

1. 「有効応募分析 → 取込状態を確認」。前回の`STAGING`が残り、他ユーザーの更新が実行中でない場合だけ「中断したCSV取込を破棄」。`PUBLISHING`／`RECOVERY_REQUIRED`の場合は、旧データ復旧フローを先に実施。
2. Google Apps Scriptエディタで`04_CsvUpload.gs`、`05_CsvPublish.gs`、`CsvImport.html`を上記GitHub最新版へ**全文差し替え**。保存後、スプレッドシートを再読込。
3. 最初は複製したテスト用スプレッドシートと、架空の応募・求人CSVで「内容を確認 → 全件更新」。
4. 正常終了したら、`20_突合データ`、`93_求人分析マスタ`（非表示）、`94_画像マスタ`（非表示）の行数と「取込状態」がREADYかを確認。
5. その後、必要なら元の実CSVで再実行し、表示された**ブラウザ内処理／準備／送信／反映**の秒数を控える。画面上の2,453件／2,450件一致と同等か、書式が崩れないか確認。
6. 失敗した場合は、エラー表示・発生フェーズ・経過時間・取込状態を控える。**応募者の氏名や元CSVの個人情報そのものをエラーログに貼らない**。
